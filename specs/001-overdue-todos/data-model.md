# Data Model: Overdue Todo Items

**Feature**: Overdue Todo Items  
**Date**: 2025-12-12  
**Phase**: 1 - Design & Contracts

## Overview

This feature does not introduce new entities or modify the existing data model. It adds **calculated fields** (computed client-side) to determine overdue status based on existing todo data.

## Existing Entity: Todo

### Schema (No Changes)

The existing Todo entity already contains all required fields:

```typescript
Todo {
  id: string           // Unique identifier
  title: string        // Todo title (max 255 chars)
  dueDate: string?     // ISO 8601 date string (optional)
  completed: boolean   // Completion status
  createdAt: string    // ISO 8601 timestamp
}
```

**Storage**: SQLite database via backend API (no schema changes required)

### Calculated Fields (Client-Side Only)

These fields are **computed in the UI** and are not stored in the database:

```typescript
// Computed in TodoCard component or utility functions
isOverdue: boolean      // true if (dueDate < today) AND !completed
daysOverdue: number     // Days between dueDate and today (only if isOverdue)
```

**Calculation Rules**:
1. `isOverdue` = `true` when:
   - Todo has a dueDate (not null/undefined)
   - Todo is incomplete (completed = false)
   - dueDate < current date (normalized to midnight)
   
2. `daysOverdue` calculated only when `isOverdue = true`:
   - `daysOverdue = Math.floor((today - dueDate) / (1000 * 60 * 60 * 24))`
   - Returns integer number of days

## Validation Rules (No Changes)

Existing validation rules remain unchanged:
- `title`: Required, max 255 characters
- `dueDate`: Optional, must be valid ISO 8601 date if provided
- `completed`: Required boolean, defaults to false
- `id`: Generated by backend
- `createdAt`: Generated by backend

## State Transitions

### Overdue Status Transitions

```
Todo Created (incomplete, dueDate=future)
  ↓
Time Passes (dueDate becomes past)
  ↓
Todo becomes Overdue (isOverdue=true)
  ↓
User marks complete
  ↓
Todo no longer Overdue (isOverdue=false)
```

**Transition Triggers**:
- **Time-based**: Page load/refresh recalculates overdue status
- **User action**: Marking todo complete immediately removes overdue status
- **Edit action**: Changing dueDate recalculates overdue status

### Edge Cases

| Scenario | isOverdue | daysOverdue | Rationale |
|----------|-----------|-------------|-----------|
| dueDate = null | false | 0 | Cannot be overdue without due date |
| completed = true, dueDate = past | false | 0 | Completed todos are never overdue |
| dueDate = today | false | 0 | Due today is not overdue (< today) |
| dueDate = yesterday | true | 1 | One full day has passed |
| dueDate = 5 days ago | true | 5 | Five full days have passed |

## Data Flow

### Read Operations (No API Changes)

```
Frontend: GET /todos
  ↓
Backend: Returns todos with dueDate field
  ↓
Frontend: Calculates isOverdue and daysOverdue for display
  ↓
Frontend: Applies conditional styling
```

### Write Operations (No Changes)

Existing CRUD operations remain unchanged:
- `POST /todos` - Create with optional dueDate
- `PUT /todos/:id` - Update (can modify dueDate)
- `DELETE /todos/:id` - Delete
- `PATCH /todos/:id` - Toggle completed status

## Database Schema (No Changes)

No migrations or schema changes required. Existing todo table structure is sufficient:

```sql
-- Existing schema (no changes)
CREATE TABLE todos (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  dueDate TEXT,           -- ISO 8601 date string
  completed INTEGER NOT NULL DEFAULT 0,  -- SQLite boolean
  createdAt TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

## Client-Side Data Structure

### Enhanced Todo Type (TypeScript notation for clarity)

```typescript
// Received from API
type TodoDTO = {
  id: string;
  title: string;
  dueDate: string | null;
  completed: boolean;
  createdAt: string;
};

// Enhanced in UI with calculated fields
type TodoViewModel = TodoDTO & {
  isOverdue: boolean;      // Calculated
  daysOverdue: number;     // Calculated
};
```

**Note**: Project uses JavaScript, not TypeScript. These type definitions are for documentation only.

## Performance Considerations

### Calculation Complexity
- **isOverdue**: O(1) - simple date comparison
- **daysOverdue**: O(1) - arithmetic operation
- **List rendering**: O(n) where n = number of todos
- **Expected performance**: < 1ms for 1000 todos

### Caching Strategy
- **Initial approach**: Calculate on every render (fast enough)
- **Future optimization** (if needed): useMemo for calculated fields
- **No server-side caching**: Single-user app, calculation is trivial

## Summary

This feature introduces **zero data model changes**. It leverages the existing todo entity's `dueDate` field to calculate overdue status client-side. This approach:
- Minimizes implementation complexity
- Avoids backend changes and migrations
- Keeps calculations close to presentation layer
- Maintains single source of truth (dueDate field)
- Allows easy future enhancement if server-side calculation becomes necessary
